# metatidy

轻量音乐元数据工作台，提供以下功能：

1. **元数据编辑** —— 浏览/检索全库，改字段前先看差异，确认后才落盘；支持批量。
2. **元数据搜索（刮削）** —— 一个入口并行查 13 个数据源，候选按分数排序、逐字段挑选写入。
3. **按目录层级整理移动** —— 用可配置模板（`{语言}/{歌手}/{专辑}/{曲序} - {标题}`）生成计划，预览确认后才动文件。
4. **歌手头像** —— 按需获取 Last.fm 头像，浏览已保存图片和同步记录，核对 Navidrome 中的具体歌手后确认上传。
5. **疑似重复曲目核对** —— 集中比较同歌手、同曲名的多个文件，核对版本、格式、时长和路径，逐项加入现有选择。
6. **按文件夹浏览** —— 从目录层级定位音乐，查看曲目数与容量，将目录范围与搜索、标签筛选组合使用。

Web 界面，单容器部署，适合放在 NAS / 小主机上长期跑。

## 为什么它不卡

同类工具卡在「每次打开列表都去读音频文件」。metatidy 的做法是**索引优先**：

- 扫描只做一次，之后按 `mtime + size` **增量**跳过未变动文件；解析多线程、写入单线程。
- 浏览、搜索、过滤、排序**全部只查 PostgreSQL**（`pg_trgm` 索引），音频文件一个都不碰。
- 有个**快速扫描**模式：只从目录结构建索引、完全不打开文件。云盘上「首次读标签约 10 秒/文件」，
  一万首要 20 多小时；快速扫描下先出列表，等你真要编辑某几首时只读那几首。
  点击右上角「扫描音乐库」展开扫描选项，再勾选 **快速扫描**；也可以同时勾选「全量重扫」，按目录结构重新建立索引；
  也可以直接打接口：`curl -X POST http://<主机>:8080/api/scan -H 'Content-Type: application/json' -d '{"fast":true,"prune":true}'`。
- 列表接口不返回封面二进制；封面走独立接口，按需生成并在磁盘缓存 AVIF 缩略图。
- 扫描 / 批量刮削 / 整理移动都是后台任务：任务行落 PostgreSQL，实时进度写 Redis，
  前端轮询，HTTP 请求永不阻塞。
- 每个数据源独立并发 + 独立超时（整源 20 秒上限），慢源不影响其它源出结果。

两万首规模下列表翻页与搜索基本无感。

## 快速开始（Docker）

> 镜像已公开：`docker pull ghcr.io/jasonb589/metatidy:latest` 直接可用，不需要登录。

### docker compose（推荐）

```bash
git clone https://github.com/jasonb589/metatidy.git   # 或者自己写一份 compose
cd metatidy
# 编辑 docker-compose.yml：把 ./music 换成你的真实音乐目录；生产环境记得改掉 postgres 默认密码
docker compose up -d
```

compose 里已经带上两个依赖服务，不用你另外装：

- `postgres`：索引本体（曲目、任务、整理计划、设置、别名库），数据落在宿主的 `./pgdata`。
- `redis`：后台任务的实时进度（键 `metatidy:job:{id}`，TTL 7 天），数据落在 `./redisdata`。

### docker run（单容器，Postgres 与 Redis 自己准备）

```bash
docker run -d --name metatidy \
  -p 8080:8080 \
  -v /你的/音乐目录:/music \
  -v /你的/缓存目录:/data \
  -e DATABASE_URL="postgres://user:pass@你的PG:5432/metatidy" \
  -e REDIS_URL="redis://你的Redis:6379" \
  -e METATIDY_SCAN_WORKERS=4 \
  -e TZ=Asia/Shanghai \
  --restart unless-stopped \
  ghcr.io/jasonb589/metatidy:latest
```

打开 `http://<主机IP>:8080/`。界面右上角有**浅色 / 深色**切换，默认跟随系统，手动切过一次后会记住。

### 在 Arcane / Portainer 里显示图标

镜像里带了图标（就是界面那个 favicon，`app/static/icon.svg`）。**直接指向你自己的服务即可**，不依赖任何外部地址：

```yaml
services:
  metatidy:
    labels:
      # 换成你的 NAS 局域网地址 + 你映射的端口（例如映射的是 8286:8080 就写 :8286）
      com.getarcaneapp.arcane.icon: "http://<你的NAS地址>:8286/icon.svg"
```

- Arcane 认的键是 `com.getarcaneapp.arcane.icon`（另有 `-light` / `-dark` 变体）；也可以在 compose 里用项目级块 `x-arcane: { icon: "…" }`。
- 图标 URL 是**浏览器**去加载的，所以用局域网地址就行；仓库若是私有的，raw 链接匿名取不到，想让公网也能看到就用自己服务的地址或图床。

- `/music`：要扫描和整理的库，**需要读写权限**（写标签、移动文件）。
- `/data`：封面与 AVIF 缩略图缓存（索引在 Postgres 里，不在这）。
- 默认开启**自动增量扫描**：启动后会补扫一次音乐库，之后新增、修改音乐会自动入库；默认读取真实标签。
  **云盘用户请在首次启动前设置 `METATIDY_AUTO_SCAN_FAST=1`**，自动扫描只从目录建索引；
  或设 `METATIDY_AUTO_SCAN=0`，再进入界面手动选择「快速扫描」。已有的快速索引若要补读全库真实标签，
  请手动勾「全量重扫」并关闭「快速扫描」。

### 封面与 AVIF 缩略图存在哪里

扫描只把「是否有内嵌封面」等元数据写入索引。浏览曲目时，封面接口才按需读取音频里的图片并生成缓存：

| 内容 | 容器内路径（默认） | 处理方式 |
| --- | --- | --- |
| 界面缩略图 | `/data/thumbs/{曲目ID}-{尺寸}.avif` | 真正编码为 AVIF；128 / 256 / 512 像素三档，保持比例，不放大小图 |
| 原图缓存 | `/data/covers/{曲目ID}.original` | 请求原图（`size=0`）时保存原始字节，不改变原图格式 |
| 缓存校验信息 | 图片旁的 `.json` 文件 | 记录索引版本、实际图片类型与内容校验值，防止命中旧图或不完整缓存 |

使用仓库的 compose 时，上面两种图片都在宿主机 `./data` 下；修改 `METATIDY_DATA_DIR` 或卷映射即可换位置。
AVIF 质量设为 60，图片处理最多同时进行两份；常见 JPEG、PNG、WebP、GIF 内嵌封面可生成缩略图，动画取首帧。
生成缓存不会改写音乐文件或里面的原始封面，也不会在升级时把全库封面一次性重编码。

旧版 `.jpg` 缓存会在相应图片下次被访问、AVIF 成功生成后逐步替换。写标签、写封面或重新扫描更新索引后，
相关缓存会在下次请求时重新生成；如果外部工具保留了文件大小和修改时间，请手动「全量重扫」刷新索引。
仅删除 `thumbs` / `covers` 缓存不会删除曲库索引，之后访问图片时会重新生成。

## 功能怎么用

### 1. 元数据编辑

搜索/过滤定位曲目 → 点击编辑或勾选多首 → 在编辑面板里**修改需要调整的字段**（留空表示不改）→
点「预览变更」看逐字段的 `旧值 → 新值` → 确认后「写入」。

- 从 **0.25.1** 起，单首编辑会先显示已有的曲目资料，再补全索引中的作曲、作词、注释等字段。
  标签来自索引，实际文件中的旧值在预览时核对；加载期间输入的文字会保留，失败时可以重试。
- 批量编辑显示已知的共同值；不同内容标记为「多个不同值」，缺少资料的字段标记为「尚未载入」。
  只有你实际修改且非空的字段才会提交，未改的共同值、未知字段都不会写入。
- 修改过的字段会高亮并计数。「重置修改」恢复已载入的内容，包括歌词；留空始终表示保留原值，不能用来删除标签。
- 多歌手归一只处理本次修改的歌手字段：`周杰伦/费玉清`、`A feat. B`、`周杰伦 五月天` 可变成 `A & B`（可关）。
- 别名库会在写入前套用于本次提交的对应字段（比如把 `周杰伦` 统一成 `Jay Chou`）。
- 「覆盖已有值」关掉时，已有非空字段不会被改写。

#### 按文件夹浏览与筛选（v0.25）

在「我的曲库」点击「浏览目录」，或从命令面板打开「按文件夹浏览曲库」。窗口提供目录卡片、面包屑、
当前目录的曲目数与容量，以及直接子目录的名称搜索和分页。快速扫描建立的目录索引也会显示；
目录与统计来自数据库，不读取云盘，不显示尚未建立曲目索引的空目录。

进入目标目录后，选择「包含子文件夹」或仅查看本层，再点击「在曲库查看」。目录范围会叠加在现有搜索、
标签筛选上，保留已选曲目；筛选条会显示完整路径和范围，移除目录条件即可回到原来的筛选。
目录范围也可随「收藏筛选」保存，并在刷新页面后恢复。

「扫描此目录…」会将路径填入并展开现有扫描选项，核对快速扫描、全量重扫等选项后，再手动开始扫描。
含无法由输入框原样保留的字符或不能直接扫描的目录，仍可浏览和筛曲，但不提供扫描预填。

排序、升降序、每页数量和列表密度集中在「显示与排序」中，摘要直接显示当前设置；搜索和常用筛选保持可见。
点击外部或按 Escape 可收起设置，手机与桌面均保留键盘操作和减少动态效果支持。

#### 核对疑似重复曲目（v0.24）

在「我的曲库」点击「疑似重复」，或从命令面板打开「核对疑似重复曲目」。独立窗口会保留原曲库的筛选、分页与选择，
先按歌手或曲名查找分组，再逐文件比较专辑、格式、时长、大小、封面／歌词状态与完整路径。

匹配范围是**已经读取真实标签**、歌手和曲名均非空的曲目：忽略这两个字段首尾的普通空格与大小写，相同且至少有两份文件时列为一组。
快速扫描得到的路径推断记录不会进入结果；`Live`、`Remix` 等版本文字会保留，多歌手也不拆分。
这里只比较索引中的标签，**并未比较音频内容**，同组文件仍可能是不同录音或发行版本。

选择某一组只会打开比较。需要继续编辑或整理时，逐行点击「加入选择」，服务端会先核对整组索引版本，再追加这一首，
保留之前已选的曲目。索引在核对期间发生变化时会提示刷新，不采用过期结果。点击「审阅已选」即可接着使用已有流程。
浏览和核对只查询 PostgreSQL，不读取音乐文件或访问外部服务；此功能不删除文件、不自动挑选保留版本，也不估算可释放空间。

### 2. 元数据搜索（刮削）

选中曲目 → 勾选数据源 → 「搜索候选」。每个源给出它认为最匹配的一条，按分数合并排序。

- 置信度：**高** ≥120 分 / **中** ≥70 分 / **待确认** 其余（含标题、歌手、时长、专辑类型、翻唱/伴奏惩罚）。
- 勾选要写入的字段；**封面默认不写**（封面是替换写，勾上会把旧封面换掉，想写就手动勾「写封面」）→ 写入前仍然展示差异。
- 批量刮削：勾选多首 + 设「自动写入最低分」（填 0 则只搜索不写，人工复核）。

### 3. 按目录层级整理移动

在「整理移动」页配置两个模板：

| 模板 | 例子 |
| --- | --- |
| 目录层级 | `{language?}/{artist}/{album}` |
| 文件名 | `{track:02} - {title}` |

可用占位符（界面里点一下就插入）：

| 占位符 | 含义 | 占位符 | 含义 |
| --- | --- | --- | --- |
| `{artist}` | 歌手（已用 ` & ` 连接） | `{track}` | 音轨号，`{track:02}` 补零 |
| `{albumartist}` | 专辑艺术家 | `{disc}` | 碟号 |
| `{album}` | 专辑名 | `{year}` | 年份，`{year:4}` 截取 |
| `{title}` | 歌曲名 | `{genre}` | 流派 |
| `{language}` | 语言 | `{albumtype}` | 专辑类型 |
| `{mb_artist_id}` | MusicBrainz 歌手 ID | `{original}` | 原名（不含扩展名） |
| `{release_group_id}` | 发行组 ID | `{ext}` | 扩展名（不含点） |

**空值规则**：

- `{artist}` `{albumartist}` `{album}` `{title}` `{genre}` 为空时回退成设置里的文案（默认「未知艺术家 / 未知专辑 / 未知」），保证文件不会散落在库根目录。
- `{language}` `{albumtype}` `{year}` `{track}` `{disc}` 为空时**整段丢弃**，不会产生 `未知/` 空目录。
- 任意占位符都能写成 `{字段?}`，表示「为空就整段丢弃」，例如 `{language?}`。

**语言兜底**：如果标签里没有 `language`，会自动用「库根下第一层目录名」推断
（`.../【Music】/俄文/ADÉLA/PRIMA/x.flac` → `俄文`），只认已知语言名，拿不准就留空。
这样按 `{language}` 整理时不会把已有的语言目录压平。

**冲突策略**（目标已存在时）：

- `rename`（默认）自动改名 `歌名 (2).ext`，绝不覆盖。
- `skip` 跳过该文件。
- `overwrite` 覆盖目标。

**安全保证**：

- 先「仅演练」确认计划，再「确认执行」；执行用一次性 token，同一计划不能重复执行。
- 目标路径必须落在库根目录内，越界项直接标为 `invalid` 且不执行。
- 同计划内两首歌撞同一目标会自动错开，不会互相覆盖。
- 跨磁盘/云盘搬运时先复制、校验字节数一致，才删除源文件；任何异常都**保留源文件**并把失败明细列出来。
- 索引里的路径会随文件移动同步更新。

### 4. 歌手头像与 Navidrome 同步

进入「歌手头像」页，选择曲库歌手后，来源名称与 Navidrome 搜索名会一起填入；已配置 Navidrome 时自动查询候选。
也可手动填写来源名称，默认同步填入目标搜索名，点击获取头像时查询候选。单独修改过的目标搜索名会保留；
重新点选曲库歌手时恢复跟随。Last.fm 头像始终需要点击获取，候选中的**具体目标歌手仍须手动选择**，
对照来源图片与目标当前图片后确认同步。切换歌手会清除旧目标选择，自动查询失败时可点击「搜索目标歌手」重试。
同名歌手也使用各自的 Navidrome ID，名称相同不会自动触发覆盖。浏览本地歌手列表不会请求 Last.fm。

从 **0.23.0** 起，头像工作区分成三个视图：

- **获取与同步**：桌面并排核对来源与目标，底部统一显示当前选择及同步入口；手机自动改为纵向布局。
- **已获取头像**：按歌手搜索、分页浏览本地 AVIF 预览，并复用选定图片。复用前会重新校验 JPEG 和 AVIF 文件，
  校验成功后仍需重新选择目标、预览并确认；文件缺失或损坏时明确报错，不自动重新抓图。即使来源请求缓存已过 7 天，
  完整的本地头像仍可复用。
- **同步记录**：按来源歌手、目标歌手或同步状态筛选已提交的记录，仅显示当前 Navidrome 连接对应的记录。
  未提交的预览不会混入历史。「查看状态」只读取 MetaTidy 已保存的同步结果，不重发上传；结果待核对时可恢复界面锁定，
  确认 Navidrome 的实际头像后再结束本次。已存在另一笔待确认同步时，查看历史不会解除它的锁定。

两个记录视图在打开时才查询，浏览和搜索只读本地数据。界面包含短暂的切换与卡片入场动画，并遵循系统的减少动态效果设置。

从 **0.25.0** 起，点击来源图片或「已获取头像」中的图片可打开大图查看器，切换 JPEG 与 AVIF，
查看实际像素尺寸、获取日期及来源链接，并选择适应窗口或 100% 显示。两种格式都可以下载到本机。
JPEG 是最长边 1024 像素的本地上传图，AVIF 是最长边 512 像素的预览图；二者均经过处理，
下载并非 Last.fm 原始文件的逐字节副本。查看与下载只读取已有本地图片，不重新获取来源，也不触发 Navidrome 同步。

首次使用，在 compose 同目录的 `.env` 中填写下面三项，并取消 `docker-compose.yml` 对应环境变量的注释：

```dotenv
METATIDY_NAVIDROME_URL=http://navidrome:4533
METATIDY_NAVIDROME_USERNAME=你的Navidrome用户名
METATIDY_NAVIDROME_PASSWORD=你的Navidrome密码
```

地址必须能从 metatidy 容器访问；`navidrome` 这个服务名要求两个容器在同一个 Docker 网络中，
也可以填写 NAS 的局域网地址。反代的路径前缀可保留，例如 `https://music.example.com/navidrome`。
地址中不要嵌入账号、密码、查询参数或 `#` 片段。修改后执行 `docker compose up -d metatidy` 重建容器，
在头像页点击测试连接。Navidrome 凭据从服务端环境变量读取，不保存到网页或 metatidy 数据库；会话令牌只缓存在服务端内存。

需要 **Navidrome 0.61.0 或以上**，使用其原生头像上传接口。Navidrome 的 `EnableArtworkUpload`
默认开启，开启时普通登录用户可以上传；关闭时只有管理员可以上传。连接测试确认读权限和可识别的版本，
具体上传权限由 Navidrome 在上传时检查。图片由 Navidrome 保存并刷新，通常不需要全库扫描；客户端缓存可能稍后更新。
支持起点见 [Navidrome v0.61.0 发布说明](https://github.com/navidrome/navidrome/releases/tag/v0.61.0)，
权限配置见 [Navidrome 官方头像说明](https://www.navidrome.org/docs/usage/library/artwork/#artwork-uploads)。

Last.fm 歌手头像使用普通歌手页中的公开图片信息，**不需要 `LASTFM_API_KEY`**；下方数据源表中的
Last.fm 元数据刮削接口仍需要 API key。如果页面没有可用图片或出现验证页，界面会说明失败原因；
可以在浏览器中自行查看 Last.fm，粘贴图片的 `lastfm-img.freetls.fastly.net` 或 `lastfm.freetls.fastly.net` HTTPS 地址。只接受这两个图片域名和指定格式，
不会自动打开图集、执行验证页面或更换身份重试。

- 只提供逐位歌手的手动获取和同步，不安排全库批量抓取；所有 Last.fm 请求串行，间隔至少 **5 秒**。
- 支持 Last.fm 歌手主页最多两次同站 HTTPS 名称跳转，例如「周杰伦」跳至「周杰倫」；每一跳同样遵守请求间隔，
  来源链接显示最终歌手页。外站、登录／验证／图集页面及图片链接的跳转仍会停止。
- 成功来源缓存 **7 天**；无图、默认占位图、解析失败和暂不支持的来源图片地址缓存 **24 小时**。命中缓存不会再次请求来源。
- 遇到 HTTP 403 或验证页暂停 **1 小时**；HTTP 429 遵守 `Retry-After`，缺少有效值时暂停 1 小时。
  连续 3 次临时失败暂停 **15 分钟**；不会自动重试，冷却状态随数据目录持久保存。
- 同步确认 **10 分钟**内有效且只能提交一次。目标信息变化或图片校验失败时停止上传；连接中断、远端 5xx
  或服务重启导致结果无法确认时，先去 Navidrome 核对，再重新预览，避免重复替换。

使用本功能时部署**单个 metatidy 实例**，并持久挂载 `/data`。限速和重启恢复按单实例设计。

| 内容 | 容器内路径（默认） | 用途 |
| --- | --- | --- |
| 歌手头像预览 | `/data/artist-portraits/{UUID}.avif` | 最长边 512 像素的真实 AVIF，供网页核对 |
| 上传图片 | `/data/artist-portraits/{UUID}.jpg` | 最长边 1024 像素的 JPEG，确认后发给 Navidrome |
| Last.fm 请求保护状态 | `/data/lastfm-portraits/gate.json` | 保存请求间隔、失败次数与冷却期限 |

图片与内容摘要独立保存，预览和同步记录在 PostgreSQL 中；获取和同步头像不会改写音频标签。
上传图由 Last.fm 图片等比例缩小并重新编码为质量参数 90 的 JPEG，小图不放大、不裁剪，透明区域铺白底；
它并非原始文件的逐字节副本。网页 AVIF 预览从这份上传 JPEG 生成。
成功缓存的 7 天是请求复用期限，图片文件不会到期自动清理。

## 登录保护（`METATIDY_PASSWORD`）

**不设这个变量，界面就是完全开放的**：任何能连到你 NAS 端口的人都能改标签、按模板移动文件
（后者不可撤销）。设了它就启用密码登录：

- 打开界面先弹登录框，**通过之前前端一个数据请求都不发**（不会先闪一屏空表格）；
- 口令对了下发 HttpOnly 会话 Cookie（`metatidy_session`），默认有效期 30 天；
- 会话存在 PostgreSQL 的 `sessions` 表里 —— 所以**退出登录是真的撤销**（删行），重启容器也不丢登录态；
- 连错 5 次锁 5 分钟（按来源 IP 计数，成功登录即清零）；
- 顶栏显示登录状态；没设口令时显示红色的「未设密码」提醒。

几个刻意的取舍：

| 行为 | 原因 |
| --- | --- |
| `/api/health` 保持匿名可用 | 否则容器探针与 `--healthcheck` 会把一个健康实例判死 |
| 静态 HTML/JS 不拦，数据全在 `/api/*` 后面 | 未登录拿到的是空壳界面 + 登录框，页面本身不含任何数据 |
| Cookie 默认不带 `Secure` | 家用场景基本是局域网 http，带上反而登不进去；走 HTTPS 时设 `METATIDY_COOKIE_SECURE=1` |
| 口令在内存里定长比较，不存哈希 | 口令只存在于容器环境变量，没有落盘的哈希可存；比较用定长实现，避开时序侧信道 |
| 认证不依赖 Redis | Redis 挂了顶多丢任务进度，不该把人锁在门外 |

### 挂在反代后面（限速要按真实客户端 IP）

前面挂了 Nginx Proxy Manager / Traefik 这类反代时，容器看到的来源 IP 永远是反代那一个（例如
`172.19.0.1`），于是「连错 5 次锁 5 分钟」就变成**全局**的：有人在公网猛试密码，会把你自己也锁住。

给容器加一个环境变量即可（反代默认会带 `X-Forwarded-For`，NPM 就是默认带的）：

```
METATIDY_TRUST_PROXY=1
```

- **Arcane**：项目 → metatidy → 「配置」里给 metatidy 服务的 `environment:` 加这一行，保存后重新部署；
  如果它是按「容器」管理的，就在该容器的环境变量里加。
- **验证**：登录一次，看容器日志里的 `登录成功：来源 …` —— 应该显示你的真实 IP，而不是 `172.19.0.1`。
- **直接把端口暴露出去时不要开**：那样任何人都能伪造 `X-Forwarded-For` 来绕过限速。

### 反代/CDN 缓存静态 JS 会出什么事

这套前端没有构建步骤，文件名不带内容哈希。如果前面挂的反代/CDN 按扩展名缓存 js/css，部署后
浏览器可能拿到「**新 HTML + 旧 JS**」——旧 JS 不认识登录接口，界面只会弹一句「请先登录」，
登录框永远不出现（真实踩到过：openresty 把旧 `app.js` 缓存到第二天 00:30 才刷新）。

已经做了两层防护，不改反代也能登录：

1. 静态资源统一带 `Cache-Control: no-cache, must-revalidate`：用前必须回服务器校验，配合
   `ETag`/`Last-Modified` 只是一次 304；
2. **登录框由 `index.html` 里的内联脚本兜底**（HTML 不被缓存）：即使静态 JS 是旧版本，登录框
   照样出得来，登录成功后整页重载一次就能用。

顺手建议：把反代对该站的 js/css 缓存关掉，或改成按需回源（nginx 里类似
`proxy_cache_bypass $cookie_metatidy_session;`）。

Rust 后端（需要 Rust 1.85+；依赖服务用容器起最省事）：

```bash
docker compose up -d postgres redis      # 只起依赖，不跑应用
export DATABASE_URL="postgres://metatidy:metatidy@127.0.0.1:5432/metatidy"

```

自检与测试（都不需要真实音乐文件，真实音频样本由 ffmpeg 现场生成）：

```bash
cd backend-rs
cargo test --release                       # 单元测试：打分表/模板/移动安全底线/标签读写…
cargo run --release -- --selftest          # 真 Postgres + 真 Redis + 真实 HTTP + lofty
```

## 曲库视图、任务与存储诊断

- 曲库提供**列表 / 封面**两种视图。封面卡片每张代表一首曲目，共用搜索、筛选、分页和跨页选择；
  可直接编辑或进入刮削。卡片按需请求 256px AVIF，列表仍使用 128px 缩略图。
- 列表可以切换**舒适 / 紧凑**密度。视图和密度保存在当前浏览器，下次打开会继续使用。
- **最近索引**按最后索引时间倒序排列并保留当前筛选；全量重扫也会更新时间，所以它不等同于文件最初加入曲库的日期。
- 任务中心可展开查看新增、更新、跳过、失败数量以及扫描目录、触发方式和错误详情。任务轮询保留展开状态；
  页面和封面使用短暂过渡，遵循系统的“减少动态效果”设置。
- 偏好设置新增**存储与运行状态**：音乐原文件、图片缓存、PostgreSQL 索引与设置分别说明。
  缓存用量在首次打开设置或点击“刷新用量”时读取，不随 15 秒状态轮询反复统计。
- **检查缓存写入**会以应用当前用户为数据根、原图和缩略图目录创建缺少的目录，
  各写入一个随机临时文件后立即清理；失败时展示原因，不修改权限或音乐文件。
  **复制诊断信息**包含路径、用量与检查结果，不包含数据库连接串或登录口令。
- 整理设置、歌手别名和专辑别名分别保留未保存草稿，切换页签或刷新状态不会覆盖输入；
  “放弃修改”只还原对应区块。刷新整个网页或关闭标签页仍会丢弃未保存草稿，浏览器会在存在草稿时提示。

存储诊断接口为 `GET /api/storage`，显式写入检查为 `POST /api/storage/check`，都沿用应用的登录保护。
统计只查看缓存目录中的图片文件，不包含 JSON 校验文件；大目录达到条目或时间预算时显示部分统计。
容器内无法可靠得知宿主机的绑定路径，需对照实际 Docker 主机上的 Compose 卷映射。

### 曲目详情与常用筛选（0.15.0）

- **查看曲目详情**：点击列表歌名或封面卡片，查看 512px AVIF 大封面、完整索引标签、文件路径、
  大小、时长及索引时间。面板里的前后箭头在当前页结果内浏览；编辑与刮削可从面板直接进入。
  详情展示“已读标签 / 快速索引”和文件可访问状态，失败时保留列表快照并支持重试。
- **歌词按需读取**：打开详情不会自动读取歌词，点击“读取歌词”后才访问原文件。
  复制路径在普通 HTTP 等无法使用剪贴板的环境下，会选中路径并提示手动复制。
- **常用筛选收藏**：保存搜索、筛选、排序、每页数量、视图和密度，一键恢复；最多保存 12 个，

## 自动增量扫描

默认开启。把音乐放进已经挂载的音乐目录后，文件系统通知会触发自动扫描：

1. 合并同一批新增、修改与重命名事件，只扫描受影响的目录；临时文件改名成正式音频、整张专辑目录移入也会处理。
2. 等待 **10 秒没有相关新事件**，再间隔 2 秒比较文件大小与修改时间。整目录移入会比较目录内音频的元数据，
   检测到仍在变化就继续等待，减少读到尚未复制完的文件。
3. 建立普通后台扫描任务，默认读取真实标签，并按 `mtime + size` 跳过未变文件。任务在「任务中心」可见，
   自动和手动扫描共用扫描锁，避免同时重复处理。

每次服务启动、目录监听恢复时，会额外补做一次**整库增量扫描**，发现停机或挂载断开期间新增的音乐；
通知队列溢出时也会补扫。此过程需要遍历目录和文件元数据，未变化的音乐不会重新读取标签。
普通文件事件只检查受影响目录；本功能没有定时整库轮询。

自动扫描**不清理缺失索引、不刮削、不写标签、不移动文件**。删除或外部改名后，旧路径记录会保留，
避免云盘短暂掉线时误清空曲库。确认挂载正常后，可手动扫描并勾选「清理已删除的文件记录」整理旧记录。
程序自身写标签或移动文件产生的通知也会合并处理；索引已同步时会增量跳过，读取文件产生的访问事件被忽略。

配置示例（改动后 `docker compose up -d` 重建应用容器）：

```yaml
environment:
  METATIDY_AUTO_SCAN: "1"                  # 默认开启；设 0 后只使用手动扫描
  METATIDY_AUTO_SCAN_FAST: "0"             # 默认读真实标签；云盘希望仅按路径建索引时设 1
  METATIDY_AUTO_SCAN_DEBOUNCE_SECS: "10"    # 静默等待时间；之后还会检查文件是否稳定
```

首次启动也遵循以上配置。云盘首次读取标签可能很慢，建议先设置 `METATIDY_AUTO_SCAN_FAST=1`；
快速模式不读取封面、时长等真实标签。之后要补读已有快速索引，请手动「全量重扫」并关闭「快速扫描」。
`/api/status` 的 `auto_scan` 字段提供监听状态、待扫目录数、最近任务与错误；目录暂时不可用时会自动重试。

### CloudDrive2 与事件链路

自动发现依赖挂载盘向容器传递文件变更通知。CloudDrive2 的通知功能属于 PRO 功能，其限制仍然适用：

- 经 CloudDrive2 上传或修改的文件才能直接产生通知；在网盘官方 App / 网页里新增的文件，CD2 不一定能立即发现。
- 在 CD2「我的文件」中刷新对应目录、让目录缓存发现变化后，才可能产生通知；需确认所用版本、挂载方式与容器都能收到。
- 没有事件的远端变更不会凭空触发自动扫描。可刷新 CD2 后观察，或使用曲库页的「只扫这个子目录」手动补扫。
  下次服务启动时也会检查当时挂载目录已可见的内容。

可用只读探测器检查通知是否真正传进了容器，不需要数据库：

```bash
# ① 直接对容器里的库目录跑（不用进容器）
docker exec -it metatidy /usr/local/bin/metatidy-server --watch-probe /music/中文/浅影阿

# ② 加 --watch-probe-self-test：会在监听目录里创建并删除一个隐藏临时文件
#    （.metatidy-watch-probe-*.tmp，非音频、不参与索引），用来确认「本机这一侧」链路是通的
docker exec -it metatidy /usr/local/bin/metatidy-server \
  --watch-probe /music/中文/浅影阿 --watch-probe-self-test
```

它会打印：目录数、宿主机的 `fs.inotify.max_user_watches`、以及实时收到的每个事件。按屏幕提示做
三步实测（CD2 Web UI / WebDAV 放文件 → 网盘官方 App 或网页放文件 → 在 CD2 里刷新那个目录），
就能确认哪些操作能被自动发现、哪些需要刷新目录或手动补扫。

**注意 inotify watch 上限**：递归监听要为**每个目录**建一个 watch，库里有 6000+ 目录时，宿主机
`fs.inotify.max_user_watches`（常见默认 8192）可能不够，不够会报 `ENOSPC`：

```bash
sysctl -w fs.inotify.max_user_watches=65536
# NAS 上要写进 /etc/sysctl.conf 或开机任务，否则重启就丢
```

监听连接失败时可在服务日志和 `/api/status` 查看错误，修复挂载或 watch 上限后程序会重试并补做增量扫描。

## 已知限制

- 支持写标签的格式：**mp3 / flac / m4a / ogg(oga/opus)**。wav/aiff/wma/ape 不写。
  mp3 与 flac 的写入路径有真实样本的自动化测试；m4a/ogg 目前没有样本，属**未验证**。
- 部分细节字段（碟号 `TPOS`、版权 `TCOP`）某些源拿不到，会留空而不是瞎填。
- 数据源现状（都是**实测**结论，不是推测）：
  - 直接可用：MusicBrainz、iTunes（4 区）、网易云、QQ音乐、酷狗、酷我、Deezer、TheAudioDB。
  - Last.fm：内置 key 已被上游吊销（HTTP 403），要用请自备 `LASTFM_API_KEY`。
  - TheAudioDB：上游没有中文曲库数据，中文歌只能靠其它源。
  - 需自备 key：Spotify / Genius / Discogs；YouTube Music 未实现。
  - 酷我的封面 URL 在上游普遍 404，它的候选可能没有封面。
- 语言兜底只认「已知语言目录名」，自造目录名不会被当成语言（宁可不猜）。
- 服务本身没有账号体系，**不要直接暴露到公网**；放在内网或前面套一层带认证的反代。
